Documento técnico: Sistema de persistencia y recuperación de trabajos (work.json)

Proyecto: WinrarPassWordCrackerByLoko
Fecha: 2026-10-16
Naturaleza: Exclusivamente de diseño — sin implementación de código.

---

1. Diagnóstico actual

1.1 Flujo de arranque

main.py
  └→ Config()                              # carga .env
  └→ DependencyInjector.build_dependencies # construye servicios concretos
  └→ Controller(path, config, dependencies)
       └→ FolderController.createInitalFolders  # OUTPUT, TEMP, INPUT
  └→ c.bruteForce()
       └→ dependencies["sequential_brute_force"].execute()
  └→ finally: c.saveLogs()                 # OUTPUT/logs_TIMESTAMP.log

1.2 Flujo de ejecución (SequentialBruteForceService.execute)

1. Valida que existen rar_path y unrar_path.
2. Calcula el total de combinaciones (PasswordCombinationGenerator.countTotal).
3. Itera for length in range(min_len, max_len + 1) llamando a _run_colony(length).
4. Cada colonia:
   - TermiteService.spawnColony → crea TEMP/TERMITES-L{length}/ con un .txt por combinación (0.txt, 1.txt, …).
   - Itera sobre todos los archivos ordenados por índice.
   - Para cada termita: lee la contraseña, prueba con WinrarService.tryPassword.
   - Si acierta: la termita sobrevive (se mueve a OUTPUT/), se extrae el contenido, retorna True.
   - Si falla: la termita muere (os.remove).
5. KeyboardInterrupt → retorna False sin persistir nada.

1.3 Hallazgos críticos relevantes para el diseño

Problema: logger.info(f"...TRY::{password}") registra la contraseña en texto plano
Impacto en persistencia: Violación de RED FLAG de CLAUDE.md. work.json no debe repetir este patrón.
────────────────────────────────────────
#: 2
Archivo:línea: SequentialBruteForceService.py:79
Problema: tracker.update(extra_info=f"trying: {password}") muestra cada contraseña en consola
Impacto en persistencia: Mismo riesgo de exposición.
────────────────────────────────────────
#: 3
Archivo:línea: TermiteService.py:67-68, 77-78
Problema: except: pass en kill y survive
Impacto en persistencia: Enmascara fallos de I/O; dificulta garantizar consistencia entre filesystem y work.json.
────────────────────────────────────────
#: 4
Archivo:línea: Config.py:37-38
Problema: except: pass en loadConfig
Impacto en persistencia: Si .env falla, la config llega vacía y silenciosamente.
────────────────────────────────────────
#: 5
Archivo:línea: WinrarService.py:26-27
Problema: except Exception: return False
Impacto en persistencia: No distingue contraseña incorrecta de fallo de infraestructura (timeout, exe corrupto). Esto es crítico:
marcar una termita como "probada" cuando en realidad hubo un error de infraestructura provocaría saltar contraseñas válidas al
recuperar.

Conclusión del diagnóstico: el estado de ejecución es completamente efímero. No existe ningún mecanismo de persistencia entre ejecuciones. Cada arranque regenera todas las colonias desde cero. La única señal de progreso intrarrun es la eliminación de archivos .txt en TEMP/, pero spawnColony usa os.makedirs(exist_ok=True) y reescribe todos los archivos, así que ni siquiera el filesystem ofrece recuperación confiable hoy.

2. Comparación arquitectónica

Alternativa A — Filesystem como fuente de verdad

Idea: Los archivos .txt restantes en TEMP/TERMITES-L{length}/ representan el progreso. work.json solo guarda identidad y estado de alto nivel. Al recuperar, se escanea TEMP/ para reconstruir qué falta.

┌────────────────────────────────────────────────────────┬─────────────────────────────────────────────────────────────────────┐
│                        Ventajas                        │                             Desventajas                             │
├────────────────────────────────────────────────────────┼─────────────────────────────────────────────────────────────────────┤
│ No requiere tracking de índices en JSON                │ TEMP/ es volátil: el SO o el usuario pueden limpiarlo               │
├────────────────────────────────────────────────────────┼─────────────────────────────────────────────────────────────────────┤
│ Progreso naturalmente granular (1 archivo = 1 termita) │ spawnColony reescribe todo — habría que modificarlo para no         │
│                                                        │ sobrescribir                                                        │
├────────────────────────────────────────────────────────┼─────────────────────────────────────────────────────────────────────┤
│ El kill ya elimina archivos — reutiliza mecánica       │ No funciona para RandomBruteForceService (no hay orden natural)     │
│ existente                                              │                                                                     │
├────────────────────────────────────────────────────────┼─────────────────────────────────────────────────────────────────────┤
│                                                        │ Dos fuentes de verdad (filesystem + JSON) pueden entrar en          │
│                                                        │ conflicto                                                           │
├────────────────────────────────────────────────────────┼─────────────────────────────────────────────────────────────────────┤
│                                                        │ Recuperar requiere escanear directorios potencialmente enormes      │
└────────────────────────────────────────────────────────┴─────────────────────────────────────────────────────────────────────┘

Alternativa B — work.json como fuente de verdad (índice-basado)

Idea: work.json tracking por índice: qué colonias están completadas, en cuál se está trabajando y hasta qué índice. TEMP/ es desechable y se regenera. Escritura atómica + flush periódico.

│                           Ventajas                           │                          Desventajas                          │
├──────────────────────────────────────────────────────────────┼───────────────────────────────────────────────────────────────┤
│ Portable y robusto — sobrevive a limpieza de TEMP/           │ Requiere gestionar frecuencia de flush                        │
├──────────────────────────────────────────────────────────────┼───────────────────────────────────────────────────────────────┤
│ Independiente de la estrategia — mismo repositorio para      │ Pequeña redundancia al recuperar (re-probar ~N termitas desde │
│ Sequential y Random                                          │  el último flush)                                             │
├──────────────────────────────────────────────────────────────┼───────────────────────────────────────────────────────────────┤
│ Escritura atómica garantiza JSON válido siempre              │                                                               │
├──────────────────────────────────────────────────────────────┼───────────────────────────────────────────────────────────────┤
│ TEMP/ sigue siendo desechable, coherente con su propósito    │                                                               │
├──────────────────────────────────────────────────────────────┼───────────────────────────────────────────────────────────────┤
│ Escalable: el bloque progress es polimórfico por estrategia  │                                                               │
└──────────────────────────────────────────────────────────────┴───────────────────────────────────────────────────────────────┘

Alternativa C — Híbrido (JSON primario + filesystem secundario)

Idea: work.json tracking por índice (como B), pero al recuperar se valida contra el estado de TEMP/. Si hay termitas restantes, se usan; si no, se regeneran y se usa el índice del JSON.

3. Arquitectura recomendada

Se recomienda la Alternativa B (work.json como fuente de verdad, índice-basado).

3.1 Nuevos componentes

src/
  Application/services/WORK/
    IWorkRepository.py              # Contrato: load, save, exists, archive
  Infrastructure/services/WORK/
    JsonWorkRepository.py           # Implementación: lee/escribe work.json atómicamente
  Models/
    WorkState.py                    # DTO/entidad del estado del trabajo
    Enums/
      WorkStatus.py                 # NEW, RUNNING, PAUSED, COMPLETED, FOUND, FAILED

3.3 Principio clave

El IWorkRepository se inyecta en SequentialBruteForceService vía constructor. Dentro de execute(), el servicio:

1. Carga el WorkState existente (si hay).
2. Valida la identidad (hash del RAR, charset, rangos, estrategia).
3. Decide: reanudar (si coincide y está en RUNNING/PAUSED), archivar y crear nuevo (si no coincide), o reportar completado (si COMPLETED/FOUND).
4. Ejecuta, actualizando y guardando el WorkState periódicamente.

El contrato execute() -> None se preserva. El Controller no cambia su lógica de delegación.

5.3 Nota sobre RUNNING vs PAUSED

Si el proceso muere abruptamente (kill, corte de energía), no habrá oportunidad de escribir PAUSED. El último flush habrá dejado state: "RUNNING". Al recuperar, se trata cualquier trabajo en RUNNING como reanudable (equivalente a PAUSED). La distinción entre RUNNING y PAUSED es informativa, no determina la lógica de recuperación.

6. Escenarios de recuperación

6.1 Primera ejecución

- work.json no existe.
- JsonWorkRepository.load() retorna None.
- Se calcula la identidad (hash del RAR, charset, rangos).
- Se crea WorkState(state=NEW), se guarda.
- Se transita a RUNNING y se ejecuta normalmente.

6.2 Reinicio (reanudación exitosa)

- work.json existe, JSON válido.
- Se carga WorkState.
- Se recalcula la identidad actual y se compara con la almacenada.
- Coinciden (mismo hash, charset, rangos, estrategia).
- state es RUNNING o PAUSED.
- Se reanuda: saltar completed_colonies, en current_colony saltar termitas 0..current_colony_index, continuar desde current_colony_index + 1.
- Se transita a RUNNING.

6.3 Interrupción abrupta (kill / corte de energía)

- El último flush dejó work.json con state: "RUNNING" y current_colony_index: N.
- Al reiniciar, se carga el estado. Se reanuda desde N + 1.
- Trabajo redundante: las termitas entre el último flush y la interrupción real se re-probarán. Esto es seguro (no causa saltos de contraseñas válidas), solo ligeramente ineficiente. El máximo redundancia es flush_interval termitas.
- Caso especial — interrupción durante escritura de work.json: la escritura atómica (escribir a work.tmp.json + os.replace) garantiza que work.json siempre tiene el último estado válido completo. Si el proceso muere durante la escritura del temporal, work.json queda intacto con el estado anterior.

6.4 Trabajo completado (COMPLETED o FOUND)

- work.json existe con estado terminal.
- Se reporta al usuario: "El trabajo anterior ya finalizó (contraseña encontrada / no encontrada)".
- Decisión del usuario: archivar y empezar uno nuevo, o simplemente salir.
- No se re-ejecuta automáticamente.

6.5 Configuración modificada

- work.json existe, pero la identidad no coincide (ej: cambió el RAR, el charset, o los rangos).
- Se archiva el trabajo anterior: work.json → work.archived.{timestamp}.json.
- Se crea un nuevo trabajo desde cero.
- Se loguea: WARN: WorkService::previous_work_archived::identity_mismatch.

- JsonWorkRepository.load() falla al deserializar (json.JSONDecodeError).
- Se hace backup: work.json → work.corrupt.{timestamp}.json.
- Se loguea: ERROR: WorkService::corrupt_work_file::backed_up.
- Se notifica al usuario y se inicia un trabajo nuevo desde cero.
- No se aborta la ejecución — se degrada graciosamente.

7.3 Contrato IWorkRepository

IWorkRepository (ABC):
    @abstractmethod
    def load() -> WorkState | None       # Retorna None si no existe

    @abstractmethod
    def save(state: WorkState) -> None   # Escritura atómica

    @abstractmethod
    def exists() -> bool

    @abstractmethod
    def archive() -> str | None          # Renombra work.json → work.archived.{ts}.json, retorna nueva ruta

7.4 Inyección y Attack enum

El attack_mode ya se lee de .env y existe Attack.SEQUENTIAL / Attack.RANDOM. La identidad del trabajo incluye attack_mode, así que un trabajo SEQUENTIAL no se confunde con uno RANDOM. Cuando se implemente RandomBruteForceService, este también recibirá IWorkRepository y manejará su propio bloque progress (polimórfico).

9. Recomendación final

Alternativa seleccionada: B — work.json como fuente de verdad (índice-basado)

Justificación

1. Fiabilidad: TEMP/ es volátil por diseño (es una carpeta temporal). Confiar en ella como fuente de verdad (Alternativa A) es frágil. Un work.json atómico en la raíz del proyecto sobrevive a cualquier escenario de interrupción.
2. Compatibilidad de contratos: La Alternativa B requiere los cambios mínimos al código existente. El contrato execute() -> None se preserva. Controller no cambia. IBruteForceService no cambia. Solo SequentialBruteForceService y DependencyInjector se modifican, y de forma aditiva.
3. Escalabilidad: El bloque progress es polimórfico por estrategia. Cuando se implemente RandomBruteForceService, reutiliza el mismo IWorkRepository y JsonWorkRepository. Solo cambia el contenido de progress. Las Alternativas A y C acoplan el progreso al filesystem, que no tiene orden natural para RANDOM.
4. Granularidad de recuperación controlable: El flush_interval permite balancear overhead de I/O vs. redundancia al recuperar. Para este proyecto educativo (charsets pequeños, combinaciones moderadas), un flush cada 100 termitas es negligible en performance y limita la redundancia a 100 re-intentos en el peor caso.
5. Consistencia garantizada: La escritura atómica (temp + os.replace) elimina la clase entera de "JSON parcialmente escrito". Es el patrón estándar y suficiente para este caso — no se justifica introducir una base de datos o WAL.
6. Seguridad: work.json no almacena la contraseña. Solo password_found: bool. Cumple con la RED FLAG de CLAUDE.md.
7. Simplicidad: La Alternativa C (híbrido) duplica la complejidad de reconciliación sin beneficio tangible en el estado actual del proyecto. Se puede evolucionar de B a C si el futuro lo requiere, pero YAGNI aplica hoy.
